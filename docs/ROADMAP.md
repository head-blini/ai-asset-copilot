## 순서와 단계 간 의존성

Phase 8은 Paper Trading 기반을 개발하는 단계다. 전략의 실제 검증 순서는 **Backtest → Live-market Paper Trading → 제한적 실전**이며, Phase 9와 Phase 10을 건너뛰지 않는다. 정량적 승격·중단 기준은 OD-08에서 확정하고, 성능이 확인되기 전 실제 주문 기능을 활성화하지 않는다.

Phase 5의 AI Shadow는 저장되거나 수동 제공된 제안으로 실행 계약을 검증할 수 있다. 실제 AI Provider 연결은 Phase 7이다. Phase 6의 1/3/6개월 Review 기록 요구는 Scheduler 도입을 강제하지 않는다. 자동 일정은 필요할 때 Phase 11에서 결정한다.

Phase 12에 Broker credentials나 adapter가 존재해도 실주문 권한을 의미하지 않는다. 실전 주문 활성화는 Phase 13에서 다룬다. 미국 실제 포트폴리오는 전체 로드맵에서 분석·의사결정 보조 대상으로 유지한다.

## 사용자 도달점과 실제 사용 경로 — R0 계획 제안, 승인 대기

아래 도달점은 Phase 0–13을 대체하는 상태 체계가 아니다. 사용자 결과가 내부 API만으로 달성됐다고 판단하지 않도록 입력·대사·보고·운영 연결을 추적한다. **M1의 최소 보고를 Phase 11 전체보다 앞서 설계·구현하는 순서 조정은 승인 대기**다. 이유는 현재 분석 API만으로 실제 자산을 지속해서 입력·확인할 수 없기 때문이다. 영향은 Phase 4의 기존 완료 조건을 줄이는 것이 아니라, Phase 1–4 산출물을 사용자가 확인할 수 있는 입력·보고 경로와 연결하는 추가 작업이다. Phase 11의 Dashboard/Daily/Weekly Report 전체 범위는 유지한다. Phase 4의 미해결 기준이 닫히기 전 Phase 5의 실질 구현은 시작하지 않는다.

## 사용 채널과 운영 의존성

미래 제품의 주 경로는 모바일·PC 대응 웹앱, 텔레그램은 알림과 허용된 간단 조회다. 초기 계산·보고 프로그램은 맥미니에서 실행한다. 브라우저/텔레그램 접속 수명과 프로그램 실행 수명을 분리하고 로컬 접근과 재시작·복구를 먼저 검증한다. 이후 인증·원격접속·조회 권한·개인정보 보호를 별도로 검증한다. 구체적 웹 프레임워크는 [OD-19](../PROJECT_SPEC.md#15-open-decisions)에서 결정한다. 이 결정은 Phase 11의 보고·화면 범위를 유지하며, BUD-01의 오프라인 보고가 웹앱 구현을 뜻하지 않는다. 네이티브 앱, 공개 배포, 텔레그램 승인, 자동 송금·주문은 승인된 범위가 아니다.

## Budget / Cashflow Planning 확장

2026-09-25 사용자 요청으로 개인 현금흐름·예산·목표저축을 제품 범위에 추가했다. **BUD 기능은 아직 구현되지 않았다.** 이 BUD 작업은 Phase 0–13의 번호와 각 완료 조건을 변경하지 않는다. 기존 M1의 미국 계좌 입력→대사→평가→Policy→최소 보고는 유지한다. BUD-04에서 그 검증된 미국 자산 상태와 개인 예산을 함께 보고하되, BUD-01의 순수 계산은 M1이나 P4-06/07의 완료에 불필요하게 종속시키지 않는다. 반대로 실제 투자 자금 연결인 BUD-03은 승인된 예산, 가용현금, 입력·대사 및 기존 Policy/Risk 경계가 검증된 뒤에만 진행한다. P4-05 별도 후보 개발과 BUD 문서 검토는 R0가 미병합이어도 병행할 수 있다. 이는 구현·문서 변경을 분리하면서 Phase 4 또는 M1 완료 판정을 앞당기지 않기 위한 순서 조정이다. Phase 5–13과 그 gate는 그대로 유지한다.

### BUD-01 다음 코드 작업 계약

- **목적/입력:** 한 사람의 한 달에 대해 수동 작성한 가상 KRW 실수령 입금(실제/확정 예정/불확실 구분), 개시 가용현금과 기존 보호 잔액, 날짜별 고정비·생활비·자유지출·카드 사용/납부·부채 원금/이자·계좌 간 이동, 주택·노후 등 목표 유형/선택적 금액·기한/우선순위/기존 적립·이번 적립, 이미 지출·예약한 금액, 사용자 소유 정책, 기준 월/평가 시점을 받는다. 세전액은 참고 정보로만 사용하고 실수령액에서 기존 공제를 또 빼지 않는다. 실제 정책 값이 없으면 미설정으로 남긴다. 가상 예제 숫자는 운영 기본값이 아니다.
- **계산/출력:** 명시적 순서의 규칙으로 월초 배정안과 월중 잔여안을 구별하고, 일자별 입금·납부를 반영한 현금 궤적, 각 용도별 배정·이미 사용·잔여, 미배정액, 부족액과 그 원인, 계산 가능한 목표 기한까지의 필요 적립액과 납입 가능일을 반환한다. 금액·기한 미정 목표는 필요 적립액 `None`/`UNKNOWN`과 필요한 입력을 내며 확인된 소득·지출·현금흐름은 계속 표시한다. 공유 재원은 주택·노후 목표에 이중 배정하지 않고 목표·보호자금 정책 미정이면 확정 투자 가능액을 표시하지 않는다. 배정은 실제 이체가 아니다. 월말 합계가 흑자여도 월중 부족이면 부족 날짜와 금액을 표시한다. 미래 투자수익·불확실 소득·대출·미실현 이익으로 적자를 숨기지 않는다. `Decimal`·통화·출처·시각을 유지하고 입력 순서에 의존하지 않는 결과를 낸다.
- **비범위/산출물:** 순수 계산 코드, 집중된 단위 테스트, 한 번 실행해 사람이 읽을 수 있는 가상 월간 보고를 출력하는 오프라인 예제와 기존 문서의 사용 안내가 산출물이다. DB, 은행/카드 API, Toss, 세금 계산, 대출 최적화, 다중통화 예산, 실시간 결제 차단, LLM, 실제 송금·환전·주문은 넣지 않는다. 다음 코딩 PR에서 구현과 검증 결과를 제출하며 문서 변경만으로 BUD-01을 완료 처리하지 않는다.

정책 값과 입력·승인·연결의 남은 결정은 [OD-15~17](../PROJECT_SPEC.md#15-open-decisions)에 둔다. Toss 증권 API가 급여·은행·카드 내역을 제공한다고 가정하지 않는다. Toss 조회 capability 조사는 OD-14의 독립 작업이며 이 예산 범위의 외부 연동 승인이나 실계좌 호출이 아니다. BUD-01 이후는 각 단계마다 작은 코드·테스트·보고 단위로 진행한다.

BUD-01의 순수 계산·가상 입력·세 시나리오 보고는 별도 `feat/budget-monthly-foundation` 후보에서 검토 중이다. 결과는 승인·이체·주문이나 BUD-02/03 구현이 아니다. 이 후보의 테스트·CI·리뷰·병합 상태는 [STATUS](STATUS.md)에서 추적하고, 기존 완료 조건은 유지한다.

## Phase 1 권장 구현 범위

Phase 1 구현 기준과 완료 검증 범위의 기록이다. OD-01과 OD-06 중 Foundation에 필요한 결정을 해결했다.

1. 포트폴리오·계좌·자산·통화·거래·포지션의 최소 Domain과 식별 규칙을 정한다. 다섯 초기 Portfolio ID를 지원하고 계좌별 상태를 분리한다.
2. 금액·수량의 Decimal 정밀도와 반올림, Cost Basis·Average Price·Realized/Unrealized PnL의 기준, 거래 시간과 평가 시점을 결정한다.
3. 수동 입력 또는 테스트 fixture의 거래·가격으로 현금, 보유 수량, 원가, 기본 평가와 손익을 코드로 계산한다. 외부 가격·FX API는 Phase 2에서 연결한다.
4. Repository 계약과 최소 SQLite Schema를 결정하고 저장·재조회·트랜잭션의 일관성을 검증한다. ORM 필요성은 별도로 판단한다.
5. 입출금·매수·매도·수수료·소수 수량·잘못된 입력·계좌 간 격리와 저장 왕복을 테스트한다. 확정하지 않은 금융 이벤트는 명시적으로 지원하지 않는 것으로 처리한다.

완료 조건은 동일 입력에서 재현 가능한 기본 계산, 계좌 격리, 저장 후 동일 상태 복원, 금융 규칙의 문서화와 테스트다. 현재 상태 분석은 Phase 3에서 구현했다. 역사적 성과, Policy 실행, Shadow, AI, Strategy, Broker 실행은 데이터와 계약이 확보되는 후속 단계에서 추가한다.

## 모델과 검수

작업 시작 시 [OpenAI 공식 모델 문서](https://developers.openai.com/api/docs/models)와 [Codex 코드 생성 안내](https://developers.openai.com/api/docs/guides/code-generation)에서 실행 시점의 최신 Codex 가용 모델을 확인한다. 모델명은 향후 낡을 수 있다. 비용·속도보다 작업 위험도와 복잡도를 우선한다. 복잡한 구현의 기본은 GPT-6 Sol / High, 중요한 Architecture·금융 구조 검토는 GPT-6 Sol / XHigh다. 반복적이고 범위가 좁은 작업에는 필요 시 GPT-6 Luna를 사용할 수 있다.

Backtest Integrity Audit, Broker / Execution Safety Audit, 실제 자금 연결 전 최종 Safety Audit에는 GPT-6 Sol / XHigh 또는 Max를 사용한다. AI끼리의 합의는 검증 증거가 아니며 테스트·CI·실행 결과가 우선이다. 모델 사용 원칙의 원장은 PROJECT_SPEC이며, Audit만으로 인간의 자금 투입 승인을 대체하지 않는다.

제공자, 금융 계산 규칙, 정책 운영 방식, 한국 거래 비용·위험 한도, 실전 승격 기준 등의 미결정 사항은 [Open Decisions](../PROJECT_SPEC.md#15-open-decisions)에서 추적한다.
